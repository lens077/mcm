# MCM 接入 QQ 机器人开放平台

Status: wontfix

> 勘察与撰写：2026-09-01，AgentTeams `qqbot-integration` / project-scout。
> 平台事实来自队长核实的 <https://bot.q.qq.com/wiki/> 结论，本文不重复联网核对。
>
> **结论：不建议接入，且这是四个项目里最干净的一个「否」。**
> 理由不是「暂时排不上」，而是 QQ 机器人的能力与 MCM 的产品定义之间没有交集。

## 1. 这个项目是什么

面向开发者与产品经理的**桌面端项目规划工具**。写结构化大纲，得到经校验的规划视图，
导出为 XMind 与 Visio 里**可以继续编辑**的文件。

| 结论 | 依据文件 |
|---|---|
| 管线是：结构化大纲文本 → 确定性解析 → 统一模型 → 校验 → 四种联动视图 + 导出 | `HANDOVER.md` §1 |
| 壳 Tauri 2.11；核心解析/校验/布局/导出全在 Rust；前端 React 19 不持有模型状态 | `README.md`「技术构成」 |
| 原生格式 `.mcm` 正文就是大纲语法，可手工编辑、可进 Git、行级 diff 稳定 | `README.md`「它解决什么」；宪法原则 V |
| 两个 crate：`crates/mcm-core`（解析校验布局）、`crates/mcm-export`（XMind/VSDX） | 目录实测 |
| 状态：63/63 计划任务完成，10 项自动化质量门全绿 | `HANDOVER.md` 顶部；`README.md` 质量门表 |
| 尚未验证：两种导出的真实互操作性、Windows 实机 | `HANDOVER.md` §6.1、§6.2 |
| 已发布：`mcm.apikv.com` 站点 + GitHub Releases（dmg/msi/exe） | `README.md`「网站」「下载」 |

**决定性的三条产品约束**（全部来自 `.specify/memory/constitution.md`，宪法优先于一切实践）：

1. **原则 II「性能即功能」标记 NON-NEGOTIABLE**，含硬预算：安装包 ≤ 25MB、空闲内存 ≤ 200MB。
   实测当前 11.3MB / 冷启动 P95 25ms（`README.md` 质量门表）。
2. **核心功能完全离线**是宪法要求——`HANDOVER.md` §7 在解释为什么不做自然语言 AI 生成规划时
   原文写着「理由是宪法要求核心功能完全离线」。
3. **原则 IV「结构化模型先行、校验后渲染」**：渲染是模型的纯函数，
   「UI 展示的每一条信息都必须可回溯到模型中的事实，禁止渲染层编造或推断模型中不存在的内容」。

以及 `HANDOVER.md` §7 明确**划在范围外**的清单：

> 反向导入、**实时协同编辑、云同步**、工时/资源/成本核算、界面国际化

代码侧佐证：对 `Cargo.toml`、`crates/*/Cargo.toml`、`src-tauri/Cargo.toml`
grep `reqwest|axum|tokio|hyper`，**零命中**。和 ToDo 一样，这是个没有网络栈的本地工具。

## 2. QQ 机器人对它有没有价值

**没有。** 逐条检查 QQ 机器人能提供的四类能力，对 MCM 全部落空：

| QQ 机器人能提供 | MCM 的对应需求 | 判定 |
|---|---|---|
| 把**事件**推到手机 | MCM 不产生事件。它是「打开→编辑→导出→关闭」的工具，没有后台状态机、没有长任务、没有调度器 | ❌ 无源可推 |
| 让手机**远程触发操作** | MCM 的操作全是图形编辑（拖拽、缩放、改大纲）。IM 的文本 + 按钮无法表达，也没人想在手机上排规划图 | ❌ 无操作可控 |
| **多人协作 / 群通知** | 实时协同编辑与云同步**已明确划在范围外**（`HANDOVER.md` §7） | ❌ 与路线图冲突 |
| 作为**新的输入通道**（手机发一句话生成规划） | 自然语言生成规划**已明确划在范围外**，理由是宪法要求核心功能离线（`HANDOVER.md` §7） | ❌ 与宪法冲突 |

### 唯一看似成立的场景，也不成立

`.mcm` 语法里的里程碑带日期（`README.md` 快速开始示例：`! 需求冻结 #m1 [2026-09-30] <-t5`），
任务也带日期区间（`[2026-09-01..2026-09-05]`）。于是很自然会想到：**里程碑到期提醒推手机**。

这个场景死在实现前提上：

1. **没有常驻进程。** 提醒必须在你**没打开 MCM** 的时候送达。而 MCM 是一个规划工具，
   典型使用是「排一次计划，关掉，两周后再打开」。要提醒就得造一个开机自启的守护进程。
2. **守护进程直接撞宪法原则 II。** 一个常驻后台进程 + 网络栈 + WS 长连，
   与「空闲内存 ≤ 200MB、安装包 ≤ 25MB」的 NON-NEGOTIABLE 预算正面冲突。
   当前 11.3MB 的安装包有余量，但代价不是包体积——是给一个**纯离线、纯函数式**的工具
   引入一整类新的故障模式（断连、重试、凭据过期、频控），而它换来的收益是一条日历提醒。
3. **这个需求有更好的归属。** 日期提醒是通用能力。`.mcm` 是纯文本、可 diff、可进 Git 的格式
   （原则 V），任何外部工具都能解析它的日期然后自己提醒。把提醒做进 MCM，
   是把通用能力焊死在一个不需要它的工具里。

结论：**没有任何一个场景强到值得让 MCM 长出网络栈。**

## 3. 场景、intents 与消息类型

不适用。本项目不接入，不设计 intent 订阅与消息形态。

（若强行套用，唯一候选是里程碑提醒的**主动消息**——每日 1000 条/用户的配额对这种低频场景
绰绰有余，频控从来不是这里的障碍。障碍是 §2 的「没有源、没有进程、撞宪法」。）

## 4. 接入代价评估

| 维度 | 结论 |
|---|---|
| **技术栈匹配** | ❌ 官方 SDK `botgo` 是 Go；本仓是 Rust + TS。 |
| **需新增依赖** | ❌ 从零引入异步运行时 + HTTP + WS 客户端。当前**零网络依赖**。 |
| **需新增组件** | ❌ 常驻守护进程；且要在 macOS 与 Windows **两个平台**等价实现——宪法原则 I 要求「能力集合不得有平台缺口」，CI 必须双平台构建并冒烟。这把成本直接翻倍。 |
| **公网出口** | ⚠️ 需稳定公网 IP 报白名单。终端用户的家用网络做不到——**这对一个分发给最终用户的桌面应用是结构性障碍**，不是配置问题。 |
| **备案域名** | 仅在消息带链接时需要。 |
| **与宪法冲突** | ❌ 原则 II（性能预算，NON-NEGOTIABLE）、离线要求；`HANDOVER.md` §7 范围外清单。 |

第 4 行值得单独强调：cat 和 control-tower 的 IP 白名单问题是**自用**场景，报备一个自己的
出口 IP 即可。MCM 是**发布给他人使用**的桌面应用（`README.md` 有 Releases 和官网），
每个用户的出口 IP 都不同且动态——机器人凭据也不可能随安装包分发。
这条决定了 MCM 即使想做，也只能做成「用户自己填 AppID」的高级功能，受众趋近于零。

## 5. 优先级建议与最小验证路径

**优先级：不排期，建议关闭此方向。**

不提供最小验证路径——**在这个项目上，最小验证路径本身就是浪费**。
`HANDOVER.md` §6 已经把接手后该优先处理的事排好了，都比接 IM 重要得多：

1. **§6.1 两种导出的真实互操作性（标注为最高优先级）** —— 这是产品的核心承诺
   （宪法原则 VI「导出保真」NON-NEGOTIABLE），至今未经人工验证。
2. **§6.2 Windows 平台的任何实机验证** —— 宪法原则 I 要求双平台等价，
   而 Windows 侧目前没有实机证据。
3. §6.4 项目名未定（宪法里还留着 `TODO(PROJECT_NAME)`）。

把工程量投在导出互操作性上，直接兑现产品的核心承诺；投在 QQ 机器人上，
是给一个离线工具加一条它不需要的外网依赖。

### 推翻本文结论的触发条件

写在这里，免得后人凭直觉重开：

- MCM 的产品定位从「单机规划工具」变成「团队协作平台」（即 `HANDOVER.md` §7 的
  「实时协同编辑、云同步」被移出范围外清单）；**并且**
- 因此已经存在一个服务端（有稳定公网出口、有账号体系）。

此时通知需求才真实存在，且承载它的是那个服务端，**仍然不是桌面应用本身**。
换言之：即使 MCM 将来长出协作能力，QQ 机器人也应该接在服务端，而不是接在这个仓里。
